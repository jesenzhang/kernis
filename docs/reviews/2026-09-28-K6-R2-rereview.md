## Spec

### R2-01 / P1 — v1 身份编码存在结构碰撞，错误定义可通过恢复

位置：`crates/runtime-core/src/definition.rs:797-817`；恢复比较：`crates/runtime-core/src/lib.rs:728-737`。

契约：K2 acceptance 要求有意义的拓扑或能力配置变化产生不同身份；R2 恢复必须拒绝不匹配的定义。

`append_identity_part` 给字符串加长度，但依赖列表和能力要求列表没有元素数量或不可混淆的结构编码。合法业务字符串可与结构标记相同，导致不同列表分界生成完全相同的 token 序列。

本次反例使用相同能力声明 `x / service / capabilities` 和两个相同任务 `capabilities`、`x`，仅改变第三个任务 `z`：

- A：没有任务依赖，要求能力 `(x, capabilities)`。
- B：依赖任务 `capabilities`、`x`，没有能力要求。

两份定义均通过 `validate()`；`canonical_identity()` 完全相同。用 A 启动后，以 B 和原 durable state 调用 `restore_from_definition()`，实际返回 **Ok**，没有返回 `DefinitionMismatch`。这会使恢复接受改变后的任务准入语义。

证据：[反例源文件](evidence/r2-2026-09-28/review_r2_identity.rs)、[运行日志](evidence/r2-2026-09-28/identity-probe.log)。1 个新增断言测试失败；日志包含 `restore under different semantics accepted=true`。

这是纳入联合审查后发现的 K2 既有缺陷，不是声称 K6 的 Error::source 改动引入。它阻止 K6 对 v1 身份稳定与恢复安全作最终背书。

修复要求：先记录身份格式与旧数据处理决策。只对当前串再做 hash 无法消除碰撞；不能原地修改 `kernis-run-definition-v1` 算法并冒充兼容修复，也不能只屏蔽反例中的两个字符串。必须区分结构与用户数据，保留 legacy `kernis-workflow-replay-v1`，对歧义历史数据 fail closed；迁移不能根据一个发生碰撞的旧身份猜原定义。

### R2-02 / P1 — 正常清理接受其他驱动的 DriverExit

位置：`crates/runtime-composition/src/assembly.rs:336-351`；`DriverExit` 当前仅含 runtime/status，见 `crates/runtime-core/src/async_driver.rs:209-216`。

契约：K4 生命周期要求驱动持有 Runtime 时不能独立清理 composition；最新修复强调绑定 exact driver，正常路径需要它自己的完整 registry 权威。

`release_after_owner_loss` 校验了私有绑定，但 `dispose_after_driver(self, exit)` 不核对 exit 来源，也不核对绑定 owner 状态。任意相同 store 类型的已关闭驱动均可提供这个值。

本次构造 A、B 两个 composition：A 保持 Running，B 正常关闭，将 B 的 exit 传入 A 的 `dispose_after_driver`。实际 A 的 dispose hook 执行 1 次，返回 `rollback.is_success() == true`，返回 runtime 的 run id 是 B。因此 owner-loss guard 可以经正常清理入口绕过。若注册 ID 重叠，还存在对错误 registry 执行 remove 的风险；后者是代码路径推断，当前最小反例实测的是 hook 提前执行和成功报告。

证据：[反例源文件](evidence/r2-2026-09-28/review_r2_probes.rs)、[运行日志](evidence/r2-2026-09-28/lifecycle-probes.log)。日志：`A state=Running, A disposed=1, cleanup success=true, returned run=review-b`。

修复要求：正常退出也必须携带并验证不可伪造的同一 owner 身份；仅比较可重复的 RunId 不足。拒绝时不得执行清理，也不得不可恢复地消费 composition 或传入 exit。两个 owner 都已 Shutdown、同 RunId 不同实例、owner-loss 后 foreign exit 都需覆盖。

### R2-03 / P2 — 取消 owner-loss 清理丢失剩余账本，重试误报 AlreadyReleased

位置：`crates/runtime-composition/src/assembly.rs:402-405`，另见 `cleanup_modules` 在 await 前 pop 当前 module 的实现。

契约：owner-loss 路径应 best-effort 释放保留资源，逐项记录未完成清理；`AlreadyReleased` 的公开含义是已执行一次释放且没有剩余资源。

实现先 `self.owned.take()`，再 await 外部 dispose hook。若调用方超时或取消这个 future，整个局部 ledger 被丢弃，`self.owned` 已经为 None。后续模块没有执行清理，也没有生成失败报告；重试却返回 `AlreadyReleased`。

本次 A→B 两模块反序清理，B hook 返回 Pending；poll 一次后丢弃 release future，再次调用。实际 `Err(AlreadyReleased)`，A dispose 次数为 0。

证据同 R2-02 的源文件及日志；生命周期反例合计 2 failed。

修复要求：保留跨 await 的待清理资源、正在执行的步骤和报告。不能将“已取走 ledger”当作“完成”；不得通过每次重试重新调用一个可能已有外部副作用的 hook 来假装 exactly-once。必须明确并验证中断后的恢复/未完成语义。

### R2-04 / P2 — 单一宿主入口的类型导出没有闭合

位置：`crates/runtime-loader/src/lib.rs:81-118`；契约：ADR 0007 §2、K6 inventory 的 host-facing 表与 closure rule。

实际无法导入 `runtime_loader::{RuntimeAssembly, FactoryRegistry, RUN_DEFINITION_FORMAT, RecoveryReason, StoreInvariant}`，编译返回 E0432。

`RuntimeAssembly` 是 compose/start/restore 的实际返回类型，宿主提取一个有显式返回类型的辅助函数就会遇到它；FactoryRegistry/格式常量被 inventory 列为 host-facing，RecoveryReason 和 StoreInvariant 则用于匹配恢复及错误分类的 typed payload。现有测试主要依赖局部类型推断，没有证明这些类型可被显式命名。

证据：[编译反例](evidence/r2-2026-09-28/review_r2_exports.rs)、[编译日志](evidence/r2-2026-09-28/export-probe.log)。这是至少 5 项缺口，不是宣称其他传递 payload 已全部闭合。

修复要求：按 inventory 完整审计 supported signatures / enum payload，沿已有 core→composition→loader 层次补 additive exports；使用仅依赖 runtime-loader 的独立宿主 fixture 显式声明返回类型、构造支持路径及匹配 payload。不要通过降低已承诺 API tier 来绕开缺口。

Spec 轴 findings：4；最高级别 P1（定义身份碰撞、跨 owner 清理）。
